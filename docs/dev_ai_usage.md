# 開発支援AIの使用範囲

改訂版 L808 への対応。

> 開発支援AIを使用した場合は、どの範囲の実装に使用したかを併せて記録する。ただし、前述のとおり
> 開発支援AIの出力は生成器のソースコードであり、合成データそのものではない。

将来 `THIRD_PARTY.md`（L805）に統合する。

## 最初に：これは学習データではない

**開発支援AIの出力は生成器のソースコードであって、合成データそのものではない。**

改訂版 L40 が定める判断基準は「その出力が学習データそのものになるか、学習データを作る
仕組みになるか」である。ここに記録するのはすべて後者にあたる。

生成器がどのようなデータを出すかは、学生が書いた仕様とルールによって完全に決まる（L49）。
実際、意味ASTのレコードは全件 `source: "rule"` であり、
`tests/test_no_teacher_in_semantics.py` が常時ガードしている。

## 禁止事項に触れていないこと

改訂版 L51-55 が禁じる3点について。

| 禁止事項 | 状況 |
| --- | --- |
| 開発支援AIに個々の学習サンプル（指示文・正解コード）を直接書かせる | **該当なし。** 学習サンプルは1件も生成していない。作ったのは意味ASTの生成器であり、意味AST自体もルールベースの列挙器（`unrank`）が機械的に作っている |
| 教師モデルに正解プログラムそのものを決めさせる | **該当なし。** 教師モデル未使用 |
| インターネットから取得した既存コードを合成データへ混入させる | **該当なし。** 外部コードを取り込んでいない。依存は標準ライブラリと pytest / hydra-core / mlflow のみで、いずれも生成器の実行環境であってデータには入らない |

## 進め方

**1チャンク実装ごとに人間がレビューする**方式で進めた（`RUNBOOK.md` の #1〜#10）。
各チャンクで実装・テスト・独立検証を行い、作業を止めて確認を取ってから次へ進んでいる。

計画に書かれていなかった判断は、チャンクごとに `README.md` の「実装状況」へ列挙して
レビュー対象にした。

### 開発支援AIが検出した仕様上の問題

実装の過程で、実装計画そのものの誤りや不足を検出して修正した。記録として残す。

| 内容 | 修正 |
| --- | --- |
| `odd` の正規形の根拠が誤り（`x % 2 == 1` が負数で崩れるのはC/Javaの挙動で、Pythonには当てはまらない） | 根拠を訂正。正規形 `!= 0` は維持 |
| `ast.py` という名前が標準ライブラリの `ast` を隠す（直接実行時に `ast.parse` が消える） | `semantic_ast.py` に改名 |
| リテラル具体化の一様性制約が未記載。混在させると L269 の検証等価性が壊れる | §2.4 に明記し、`uniform_literal_domain` をレコードに追加。`Binding` 型で混在を表現不能にした |
| 固定入力集合の受け入れ条件が複合ASTの識別力を保証しない（difficulty 3 で偽の衝突30件） | 受け入れ条件を2段階にし、反例駆動で解消（70件→82件） |

いずれも**人間の確認を経て**計画書に反映している。

## 記録の方針

- 生成器のソースコードは全てリポジトリに含まれ、`uv.lock` で依存が固定されている
- コーパスは `seed` と `conf/` から再現できる（`document_AST.md` §9 手順6 で確認済み）
- 由来3項目（`source` / `created_at` / `generator_version`）を全レコードに記録している
