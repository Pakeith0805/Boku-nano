# 課題文の解釈と、その根拠

実装計画 §8 に対応する。**解釈をどう決めたかは報告書の材料になる**ので、解決済みも根拠付きで残す。

出典の行番号は `芦原・倉林研究室_夏休み実習課題_Boku-nanoの開発_改訂版.md` のもの。

未解決の要確認事項はない。

## 解決済み

### 1. op数の上限は 1〜4 で確定（2026-07-30）

最終ver L111 の「1〜4個」に従う。`MAX_OPS = 4`。

以前受けていた「1〜3で固定していい（倉林先生本人に確認）」との指示は、
**学生本人の確認により 2026-07-30 に破棄され、1〜4 で確定した。**以後この判断を再検討しない。

根拠は二つ。第一に、最終verが唯一の正であり L111 が「1〜4個」と定めている。第二に、
1〜4 は目標件数に対して構造的に必要である（1〜3では空間が 12,720種類しかなく、
定数をASTに含めない方針のまま L397 の 30,000〜100,000 に届かない）。

`MAX_OPS` を 3 に下げると帯を満たす `target` が存在せず、コーパス構築が必ずエラーになる。
これは意図した safety net である。

### 2. 原版の問題例が4opだった矛盾

最終ver L163-169 で3op（`["ge","double","asc"]`）に修正され、op数上限も 1〜4 になったため解消。

### 3. `mul_k`@2 / `mul_k`@3 の除外

最終ver L275 に明記され、課題文の要件になった。あわせて `ge`@1 = `positive`
（要素が整数のため）も課題文側で追加されている。

### 4. リテラル値域

最終ver L269 で 1〜10 に確定。根拠（リテラル版＝`k`＝リテラル値での評価なので同じ検証機構が
使える）も明記された。

### 5. `behavior_hash` による可換対の検出

最終ver L258 / L516-536 で漏洩検査第5項として要件化された。

## 実装上の解釈（課題文に明記がないもの）

### 6. `behavior_hash` の衝突をコーパス構築時に除去しない

L536 が「重複が見つかった場合は、**テスト側のレコードを除外する**」と定めており、
処理場所は分割後である。構築時は記録と報告に留める。

前倒しすると L416-421 の「全数」配分（difficulty 2 の 552 など）が崩れ、
L397 の目標件数も意図せず減る。

実測：既定設定で 30,000件中 23,639件（78.8%）が衝突グループに入る。
構築時に除去すると 10,464件まで減り、目標件数の帯を大きく下回る。

`drop_behavior_duplicates=true` は用意してあるが、L816「意味重複を残す場合と除去する場合の
比較」を回すための実験条件であり、既定は off。

### 7. `always_empty` / `is_identity` のASTも除去しない

L455-461 の選抜規則に除去の指示がないため、注記して件数を報告し、判断を選抜段に委ねる。

実測：30,000件中 `always_empty` が 5,488件（18.3%）、`is_identity` が 2件
（`[add_k, sub_k]` と `[sub_k, add_k]`）。

`always_empty` の割合は無視できないので、選抜段で扱いを決めること。

### 8. 予約ペアは順序非依存と解釈した

L472 の予約で L485 の「個々の操作は学習したが、その組合せは見ていない」状況を作るには、
`[even, desc]` と `[desc, even]` の両方を除外する必要がある。したがって引き当てキーは
順序を落とした `op_set` にする。

L487 の割合の算出が `C(22,2)/C(24,4)` と**組合せ**で書かれていることとも整合する。

### 9. カテゴリ出現頻度は一様にしない

L458 が求めているのは演算子単位の頻度であり、カテゴリのop数（filter 10 : map 8 : order 3 :
slice 3）から一様にはならない。両方を `manifest.json` に出す。

実測：既定配分でのカテゴリ頻度は 3.34 : 2.68 : 1.00 : 1.01 で、op数の比とほぼ一致する。

### 10. リテラル具体化は全スロット一様と解釈した

L269 の検証等価性が成立する条件であり、L267 の日本語側の言い換え（「k以上」→「5以上」）も
単一の値を前提に書かれている。ただし複数の `k` 参照opを持つASTで、スロットごとに別の値を
許すかは課題文に明記がない。

一様と解釈した結果、使えるリテラルは各スロット値域の共通部分になる（該当は空間の 55.4%）。
混在を許す場合は参照インタプリタ側にスロット別の引数を導入する必要があり、L269 の
「パラメータ版とまったく同じ検証機構をそのまま適用できる」という利点を失う。

補足：**混在が検証不能になるかどうかはASTごとに違う。**実測では `[ge, take_first]` で58%、
`[multiple_of, mul_k]` で100%が検証不能だが、`[gt, ge]` は0%（どの混在も一様版で再現できる）。
安全なASTも実在するが、判定にはバインディング空間の全探索が要る。一律の規則にしているのは、
その判定を不要にするため。

### 11. 「最大20例」は展開時の上限と読んだ

L428（`### 意味表現の生成`）の「1意味ASTあたり最大20例」と L461（`## データの検証と選抜`）の
「一つの意味ASTにつき最大20例などの上限を設ける」は、展開時の上限とも選抜時の上限とも読め、
どちらの意味かは課題文から確定できない（`CHANGES.md` の「残る課題」2 が同じ点を挙げている）。

本実装は展開時の上限として扱っている。`k` 参照opを持たないAST（空間の9.9%、既定配分では
約4,000件）は日本語表現 × コード形式だけで20例を満たす必要がある、という申し送りが
この読みに依存する。選抜時のみの上限と読むなら、その申し送りは不要になる。

どちらの読みでもデータ規模表には到達するため、数値上の不整合は生じない。

### 12. 固定入力集合の受け入れ条件を2段階にした

実装計画 §2.5 が定める条件は「単一opのAST 24個の `behavior_hash` が全て相異なる」だが、
**これは複合ASTの識別力を保証しない。**

実測：条件を満たす70件の入力集合で、difficulty 3 に**偽の衝突が30件**あった
（固定入力集合の上では出力列が一致するのに、集合の外の入力では食い違うASTの組）。
`['add_k','abs','zero']` と `['add_k','every_other','zero']` など、`zero` のように
「特定の値を踏まないと差が出ない」opが絡む。

偽の衝突があると、L536 の漏洩検査で重複でないテスト側レコードが除外される
（漏洩する方向ではないが、テスト集合が理由なく削れる）。

そこで条件を2段階にした。

1. 単一opのAST 24個の `behavior_hash` が全て相異なる（従来どおり）
2. difficulty 1〜3 の 12,720件について、入力集合の外から見た偽の衝突がゼロ

第2段は反例駆動で満たす。食い違いを見つけたら、それを分けた入力そのものを入力集合に足す。
70件 → 82件（反例12件、3巡）で収束した。

**difficulty 4（255,024件）は未検証。**全数検証が現実的でないため、これは経験的な基準であって
証明ではない。残る偽の衝突は分割後の漏洩検査で過剰除外として現れるので、件数を報告すること。

## 分割段への申し送り

意味AST層の実測から、分割設計で確認すべき点。

- `behavior_hash` の衝突に **78.8%** のASTが関与する。L536 の漏洩検査で重複時にテスト側を
  除外すると、テスト集合がどれだけ削れるかを見積もること。ゴール条件 L734
  「未学習の意味ASTに対して100問以上」を満たせるかを確認する
- 最大衝突グループは 5,488件で、これは `always_empty` の群である
- `canonical_order` に従うASTは 23.9%。順序多様性のアブレーション（実装計画 §10）の材料になる
