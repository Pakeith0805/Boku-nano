### `boku/semantics/unrank.py` — 下降階乗基数による順位付け

**何をしている**：意味AST空間 267,744種類を配列に展開せず、通し番号 ⇄ AST を相互変換する。
`unrank(3, 1000)` なら「3op空間の1000番目のAST」が返る。

**なぜ要る**：difficulty 4 だけで 255,024種類ある。全部リストに持つとメモリを食うし、
そこから n 件選ぶのに全体を作る必要はない。番号の側で `random.sample(range(255024), 17280)` すれば済む。

**理解の勘所**：普通の位取り記数法（10進なら 100, 10, 1）と違い、**桁ごとに重みが変わる**。
先頭の桁を決めるたび、残りの選択肢が1つずつ減るため。

```
difficulty 3（24個から3個）の場合
  1桁目の重み = 23 × 22 = 506   （1桁目を決めた後、残り2桁の埋め方の数）
  2桁目の重み = 22
  3桁目の重み = 1

番号 1000 を復元する
  1000 // 506 = 1 余り 494   未使用リストの 1 番目を取り出す
   494 //  22 = 22 余り 10   残った23個の 22 番目を取り出す
    10 //   1 = 10           残った22個の 10 番目を取り出す
```

**確認のしかた**：`uv run python` で以下を叩き、紙の計算と合うか見る。

```python
from boku.semantics.unrank import unrank, rank, count
unrank(3, 1000)        # 上の手順の答えと一致するか
rank(unrank(3, 1000))  # 1000 に戻るか
count(4)               # 255024
```

`tests/test_unrank.py` が全267,744件で往復と `itertools.permutations` との一致を確認しているので、
**動作は保証されている。**理解が要るのは「なぜこれで漏れも重複もなく全部に番号が振れるのか」の部分。

**独立検証**：意味を**意図的に違う原理で**もう一度書き、全数比較した。1,779,600件が一致。

| 検証 | 件数 |
| --- | --- |
| 単一op 全数（要素−4〜4・長さ0〜4・`k` 1〜10） | 1,771,440 |
| L103 境界（±100 を含む15要素） | 240 |
| 3op操作列（12opから3個の全順列 × 6入力） | 7,920 |

原理の置き換えは、剰余→ビット検査、`sorted`→最小値の繰り返し取り出し、
スライス→添字ループ、乗算→加算の繰り返し。
`test_interp_ops.py` は期待値と実装を同じ人間が書くので思い違いが両方に同じ形で入り込むが、
原理を変えた実装ならそれを共有しにくい。

途中で1件の不一致が出たが、原因は**検証スクリプト側**の探索範囲不足だった
（`mul_k` 後の値1000を偶奇判定の探索範囲±400が覆えず偽陰性）。インタプリタ側の誤りではない。
探索を使わない定義に直して再実行し、全件一致した。

**計画に書かれておらず、実装時に決めたこと**

- **`test_interp_differential.py` を追加した（§7 に無いテスト）。**
  L281-286 の差分ランダムテストは相手のコード生成器がスコープ外のため成立せず、
  このフェーズでは手書き期待値が唯一のガードになる。その弱点を補うため常設化し、
  `document_AST.md` §7 にも追記した。コード生成器の実装後は補助に下がる
- **`boku/limits.py` を新設した。**L102-105 の入力条件の置き場所が未規定だった。
  `registry.py` は変更していない。代わりに `LITERAL_MIN/MAX == K_MIN/K_MAX`（L269）を
  `test_limits.py` で機械的に固定した
- **全opが `(xs, k)` の同一シグネチャを持つ。**`k` を参照しないopは `k` を無視する。
  `uses_k` で呼び分けるとディスパッチが分岐し、かつ参照インタプリタが `registry` の
  メタデータに実行時依存してしまう（L281-286 の独立性を損なう）
- **`run()` は構造検証をしない。**操作数や重複の検査は `validate.py`（#3）の担当（§2.7）。
  `run()` は `k` の範囲（L104）と未知op名だけを弾く。空ASTは恒等として複製を返す
- **`square` は `x * x`、`reverse` は `list(xs[::-1])`。**`op_` を全関数の接頭辞にして
  組み込み `abs` の遮蔽を避けた

**テスト**：336 passed（2.8s）。

**独立検証**：意味AST空間 267,744件を全数回し、`uniform_literal_domain` が各スロット値域の
積集合と一致すること、空にならず最小7値であること、`k`参照スロット数の分布が
26,404 / 93,110 / 102,150 / 41,040 / 5,040 であることを確認した。
`document_AST.md` §2.4 の数値と全件一致。

**設計**

- `SemanticAST` は **op列から一意に決まる値だけ**を持つ。評価が要る値（`behavior_hash`、
  `always_empty`、`is_identity`）は #6、採番と由来（`ast_id`、`created_at`、各version）は #8
- **構造検証はしない。**不正な列でも構築できる。そうしないと検証器自体をテストできない
- `from_dict` は `semantic_ast` だけを読んで派生値を再計算し、レコード側の派生値と
  食い違えば `ValueError`。レジストリ改訂後に古いコーパスを読んだことに気づける
- `canonical_json` はop列だけ。派生値も `created_at` も入れない

**この工程で分かったこと（計画に追記した）**

混在バインディングが検証不能になるかは**ASTごとに違い、事前には分からない**。実測すると
`[ge, take_first]` は混在の58%、`[multiple_of, mul_k]` は100%が検証不能だが、
**`[gt, ge]` は0%**——どの混在も一様版で再現できてしまう
（`gt@a → ge@b` は `x > max(a, b-1)` に畳めるため）。

安全なASTも実在するが、判定にはバインディング空間の全探索が要る。
267,744件について毎回それをやる代わりに「全スロット同一値」で済ませている、というのが
§2.4 の制約の本当の理由。両方の実例をテストに固定し、`document_AST.md` §2.4 にも追記した。

なおこの発見は、最初に書いたテストが失敗したことから出てきた。原因は実装ではなく、
「全ての複数スロットASTに検証不能な混在が存在する」という**私のテストの主張が強すぎた**こと。

**追加処理なしで**満たされます。

**設計**

- 桁の重みは import 時に 4×4 の表として事前計算。`perm()` の呼び出しを繰り返さない
- `rank` は未知op名と同一opの重複を弾く。構造検証は #3 の担当だが、ここで通すと
  「別のASTを指す番号」を静かに返してしまうため
- `unrank` は `tuple[str, ...]` を返す（`SemanticAST` ではない）。§2.2 の signature どおりで、
  `unrank.py` が `semantic_ast.py` に依存しない。ラップは #7 の担当

本当に一致するか調べた。

**結果：difficulty 3 に偽の衝突が30件あった。**固定入力集合では同じ指紋なのに、
実際は別の関数という組。`['add_k','abs','zero']` と `['add_k','every_other','zero']` などで、
`zero` のように「特定の値を踏まないと差が出ない」opが絡む。

原因は、`document_AST.md` §2.5 の受け入れ条件「単一opのAST 24個が全て相異なる」が
**複合ASTの識別力を保証しない**こと。偽の衝突があると、改訂版 L536 の漏洩検査で
重複でないテスト側レコードが除外される（漏洩する方向ではないが、テスト集合が理由なく削れる）。

**修正**：受け入れ条件を2段階にし、反例駆動で潰した。食い違いを見つけたら
**それを分けた入力そのもの**を入力集合に足す。

```
入力集合  70件 → 82件（境界値20 + 乱数50 + 反例12、3巡で収束）
偽の衝突  30件 → 0件（difficulty 1〜3 の 12,720件 × 外部入力 5,000件）
```

`document_AST.md` §2.5 に追記済み。**difficulty 4（255,024件）は未検証**で、
全数検証が現実的でないため経験的な基準に留まる。

**`always_empty` は誤判定していなかった。**difficulty 3 で「常に空」と判定された1,572件は、
外部入力5,000件でも全件が本当に常に空。危険な方向には倒れていない。

**設計**

- ハッシュ関数が**時刻を引数に取らない**ことで、由来情報の混入を構造的に防いでいる。
  テストは `inspect` で引数名とモジュールの import を検査している
- `behavior_hash` は出力列だけから作り、op列を混ぜない。混ぜると
  「意味ASTが違っても関数として同一なら同じ値になる」（L388）が壊れる
- 衝突は**除去せず記録するだけ**。除去は分割後（L536）であって構築時ではない

### #7 層化抽出 — 完了（2026-07-30）

意味AST空間 267,744件のうち **difficulty 4 が 95.2%** を占めるため、無作為に取ると
4操作ばかりになる。difficulty ごとに件数を決めて抽出する（改訂版 L413）。

**作ったもの**

| ファイル | 内容 |
| --- | --- |
| `boku/semantics/enumeration.py` | `Allocation`、`default_allocation`、`enumerate_asts` |
| `tests/test_stratified_alloc.py` | 配分・帯の検証・再現性 |
| `tests/test_op_frequency.py` | 出現頻度の一様性 |

**テスト**：476 passed（10.5s）。

**配分**（改訂版 L417-421 の例をそのまま既定に）

```
difficulty 1        24 種類（全数）
difficulty 2       552 種類（全数）
difficulty 3    12,144 種類（全数）
difficulty 4    17,280 種類（255,024 種類から一様抽出）
合計            30,000 種類     1〜3操作 42% / 4操作 58%
```

**実測：op出現頻度の一様性**（`document_AST.md` §2.2 の主張の確認）

| | 最大相対偏差 |
| --- | ---: |
| difficulty 1〜3（全数） | **0%（全op 1,565回ちょうど）** |
| target 30,000 全体（seed 0 / 1 / 7） | 2.07% / 3.08% / 2.09% |
| target 100,000 全体（seed 0 / 1 / 7） | 0.90% / 1.25% / 1.29% |

**均す処理は要りません。**24個のopが対称なので全数の層では厳密に一様、抽出する層でも
期待値が一様になります。改訂版 L458 が追加処理なしで満たされました。
標本が増えると偏差が小さくなることも確認済み（構成的であって偶然ではない傍証）。

カテゴリ頻度は一様になりません（filter 10 : map 8 : order 3 : slice 3）。実測は
3.34 : 2.68 : 1.00 : 1.01 で、op数の比とほぼ一致。L458 が求めているのは演算子単位なので
これは正しい挙動です（§8 確認事項⑨）。

**設計**

- **目標件数の帯（L397 の 30,000〜100,000）の外は拒否。**明示配分 `alloc=[...]` でも
  同じ検証を通すので抜け道がない。検証は Hydra ではなく `enumeration.py` 側にある（§11 の依存の層）
- 抽出は `random.sample(range(255024), n)` で**番号の側だけ**を選ぶ。空間を展開しない
- 番号は**昇順に整列**してから復元する。`random.sample` の戻り順に依存しないので
  #8 の `ast_id` 採番が安定する
- 種は difficulty ごとに独立させた。ある層の件数を変えても他の層の抽出結果が動かない。
  種を変えると difficulty 4 だけが変わることをテストで固定している
- `MAX_OPS` を 3 に下げると空間が 12,720件になり、帯を満たす `target` が存在せず必ず失敗する。
  意図した safety net（§2.2）
